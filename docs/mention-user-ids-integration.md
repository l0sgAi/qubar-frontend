# @提及(mention_user_ids)持久化与回传 — 后端对接文档

> 前端对应分支:`feature/circle-agent-management-20260830`
> 关联背景:圈子专属机器人上线后,`GET /user/search` 的全站搜索已不可见圈内机器人,因此**渲染期的提及用户必须由后端随内容回传**,搜索反查不再可靠。

## 1. 背景与现状

前端 @提及的整体机制:正文(body/content)里只存纯文本 `@用户名`,**不存 uuid**;用户在选人弹窗选中后,前端把对应 uuid 以 `mention_user_ids` 随创建接口提交。渲染时前端需要 `mentions` 数组把用户名精确解析回 uuid,才能生成可点击的提及链接(绿色高亮 + 跳转个人主页)。

目前后端**尚未持久化** `mention_user_ids`,详情/列表接口也未回传 `mentions` 字段,导致:

- 旧机制(前端渲染时用搜索接口按用户名反查)在圈子机器人场景下失效(全站搜索不可见圈内机器人);
- 用户名唯一性、改名的语义无法由前端保证。

本文档说明前端已实现的提交侧参数,以及后端需要补齐的持久化与返回值要求。

## 2. 提交侧:前端已带上 `mention_user_ids`

### 2.1 涉及接口

| 接口 | 参数位置 | 前端调用点 |
|---|---|---|
| `POST /post/create` | JSON body | 发帖页 `CreatePost.vue` |
| `POST /comment/create` | JSON body | 评论 `CommentEditor.vue`、回复 `CommentReplyEditor.vue`(两者同一接口) |

### 2.2 参数定义

```jsonc
// POST /post/create 请求体(节选)
{
  "title": "...",
  "content": "大家好 @小明 @小助 看看这个",
  "circle_id": "0192c3d4-...",        // 圈子帖子,可能为空(全站帖)
  "mention_user_ids": [               // ★ 新增
    "0192a1b2-...",                   // 「小明」的 uuid
    "0192f9e8-..."                    // 「小助」的 uuid(可能是圈内机器人)
  ]
}

// POST /comment/create 请求体(节选)
{
  "post_id": "0192...",
  "root_id": "0192...",               // 顶层评论时为 null 或等于 reply 语义的根 id
  "reply_to_id": "0192..." | null,
  "content": "@小助 收到",
  "mention_user_ids": ["0192f9e8-..."] // ★ 新增;无提及时候端不会传该字段
}
```

前端行为约束(提交前已保证,后端仍建议防御性校验):

- **与正文一致**:`mention_user_ids` 中每个 id,其用户名都以完整 `@用户名` token 形式存在于正文;前端已按正文过滤(删掉 @ 后不提交)。
- **数量 ≤ 10**:前端硬性拦截(`MAX_MENTIONS = 10`),后端如超限建议静默截断到 10,不报错。
- **元素为用户 uuid 字符串**:数组、去重、无序(前端按正文出现顺序传,但后端不应依赖顺序)。
- **可能缺省**:正文无提及时候端不传该字段(undefined),等价于空数组。

### 2.3 后端处理要求

1. **持久化**:将 id 列表与内容关联存储(独立关联表或 uuid 数组字段均可;上限 10 个)。要求**原样保留圈子机器人 id**——不要在这一步按"全局可见"过滤,可见性是搜索/推荐列表的规则,不是内容事实。
2. **防御性清洗**(沿用现有评论提及语义):去重;剔除不存在/已注销的 uuid;可剔除 @ 自己的(与现有静默过滤行为一致)。
3. **不校验与正文的对应关系**:后端不解析正文 @ token,以提交的 id 列表为准。
4. **容忍用户名变更**:存 id 不存名字,回传时映射当时最新的 username(见下节)。

## 3. 返回侧:内容接口需回传 `mentions`

### 3.1 返回格式

所有**携带正文**的内容对象,统一增加可选字段 `mentions`:

```jsonc
{
  "id": "0192...",
  "content": "@小助 收到",
  "mentions": [                // ★ 新增;无提及时可省略或返回 []
    { "id": "0192f9e8-...", "username": "小助" }
  ]
}
```

- `id`:被提及用户 uuid(即 `mention_user_ids` 里存的值);
- `username`:该用户的**当前**用户名(用户改名后回传新名字;旧正文 token 匹配不上属预期,该提及保持纯文本);
- 顺序:建议按正文中出现顺序;前端不依赖顺序;
- 只需 `id` + `username` 两个字段,不要塞完整用户对象(控制列表接口体积)。

### 3.2 需要回传 `mentions` 的接口清单

| 优先级 | 接口 | 位置 | 前端消费点 |
|---|---|---|---|
| P0 | `GET /post/detail/{id}` | 帖子详情对象 | 帖子正文提及链接化 |
| P0 | `GET /comment/list` | 每个评论对象 | 评论正文提及链接化 |
| P0 | `GET /comment/replies`(子回复列表) | 每个回复对象 | 回复正文提及链接化 |
| P1 | `POST /comment/create` 响应 | 新建的评论对象 | 前端乐观渲染新评论/回复(响应无 mentions 时退化为搜索反查) |
| P1 | `POST /post/create` 响应 | 新建的帖子对象 | 同上(当前主要靠详情刷新,建议一并带上) |

 feed 流列表(`GET /post/list`、`GET /post/home` 等)卡片不渲染正文提及,**可以不带**;若实现成本低带上也无害。

### 3.3 可见性要求(关键)

`mentions` 回传**不受 `GET /user/search` 的圈子可见性规则约束**:

- 帖子/评论里已存在的提及(含圈内机器人),对该内容的任何可见者都要回传——渲染的是内容事实,不是选人列表;
- 换言之:**内容本身可见 → 其 mentions 全量可见**,不需要按请求者/圈子做二次过滤。

这是本次对接最核心的一条:圈子里 @ 了本圈机器人,所有打开该帖的人(包括非圈子成员,只要帖子对TA可见)都应看到可点击的提及链接。

## 4. 前端消费逻辑(供后端理解,无需改动)

1. 详情/列表数据到达后,前端调 `seedContentMentions(items)` 把 `mentions` 灌入用户名→uuid 缓存(`src/utils/mentionResolve.js`);
2. Markdown 渲染完成后,`applyMentionLinks`(`src/utils/mentionDom.js`)扫描正文 `@用户名` token,缓存命中即生成 `<a class="post-mention" href="/user/{uuid}">` 链接(SPA 跳转);
3. 缓存未命中的名字(如旧内容无 mentions 字段)**保持纯文本,不再做任何搜索反查**——mentions 回传是提及链接化的唯一数据来源;
4. 通知页等无圈子上下文的表面同样只依赖 mentions 回传,前端不存在按用户名的搜索兜底。

## 5. 验收清单

- [ ] 发帖/评论/回复带 `mention_user_ids` 提交后,数据落库且包含圈内机器人 id;
- [ ] 不传 `mention_user_ids` 创建成功(向后兼容);
- [ ] 超 10 个、含非法 uuid 的请求不报 500(截断/剔除后正常创建);
- [ ] 帖子详情、评论列表、子回复列表均回传 `mentions`,且圈内机器人出现在其中;
- [ ] 对内容可见的所有请求者,mentions 内容一致(不按圈子/身份过滤);
- [ ] 用户改名后,mentions 回传新用户名,id 保持不变。

## 6. 备注(可选的后续增强)

- 若后续要支持"点击通知里的提及跳转",通知对象也建议附带 `mentions`(或复用被评论对象的 mentions);
- 若未来出现"按用户名批量精确反查"需求(覆盖无 mentions 的历史数据),可另议 `POST /user/batch` 类接口,本文档不展开。
