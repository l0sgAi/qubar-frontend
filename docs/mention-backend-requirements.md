# @提及精确绑定 — 后端需求文档

> 版本：2026-08-28 · 前端仓库：qubar-frontend · 关联代码：`src/utils/mention*.js`、`MentionPreview.vue`、`mentionResolve.js`

## 1. 背景

当前渲染侧链接化（@token → 可点击链接）靠**文本反查**：正文纯文本扫描出 @用户名，
再调 `GET /user/search` 精确比对回查 uuid。已确认的问题：

- 搜索排名/分页导致前 20 条内无精确同名 → 不建链，甚至**错链**（缩短重试命中同短名他人）
- 访客态 `/user/search` 若需登录 → 访客浏览全部不建链
- 用户改名后旧内容死链（正文存的是发帖时旧名）
- 冷缓存首刷每未知名 1~3 次搜索请求，长评论列表有请求峰值

根因：后端已持久化 `mention_user_ids` 却不回传，渲染只能靠文本猜。
本需求让后端持久化并**回传提及用户对象**，前端零搜索精确建链。

## 2. 前端工作流（已实现，供对齐理解）

1. **选人（写入侧）**：编辑器内输入 @ 触发 `GET /user/search` 选人；选中即记入
   `mentionedUsers`（去重、上限 10 人），正文插入纯文本 `@用户名`（带尾空格）。
2. **删除同步**：正文删掉 @token → `mentionedUsers` 同步移除 → 提交时不传该 id，
   后端不通知 → 防多余通知。
3. **提交**：`POST` 请求体携带 `mention_user_ids: [uuid]`（正文中仍存在的 token 对应 id，
   重复/@自己/不存在由后端静默过滤，上限 10）。
4. **渲染（读取侧）**：前端拿到内容后，把后端回传的 `mentions` 数组回灌本地缓存
   （`seedContentMentions`），链接化时 @token 与缓存精确比对 → 命中即建链跳转
   `/user/{id}`。后端没回传（旧内容正文里的 @用户名）时回退文本反查搜索，行为不变。

## 3. 后端功能需求

### F1 提及列表持久化（已有接口的字段语义收紧）

- `POST /post/create`、`POST /comment/create` 已接收 `mention_user_ids: string[]`。
- 要求：逐个校验用户存在且未注销 → 去重 → 剔除作者本人 → 上限 **10**（超出截断）→ 持久化。
- 存储：建议关系表 `(content_type, content_id, user_id, create_time)`，
  或沿用现有 JSON 列，由后端自定；**通知只对最终持久化名单发**。
- 请求里不传（前端已删光 token）→ 不落任何提及、不通知。

### F2 详情/列表回传 `mentions` 数组（本次核心新需求）

以下接口的响应内容对象需新增字段 `mentions`（可空数组，**不缺席即合规**）：

| 接口 | 位置 | 说明 |
|---|---|---|
| `GET /post/detail` | 帖子对象 | 正文提及的用户 |
| `GET /comment/list`（含回复接口 `GET /comment/replies`） | `items[*]` | 按内容各自回传 |

```json
"mentions": [
  { "id": "uuid", "username": "John Doe", "avatar_url": "https://..." }
]
```

- `id`、`username` 必填（链接目标 + 文本匹配键）；`avatar_url` 可选（渲染徽标备用）。
- 仅返回**未注销**用户；按正文出现顺序（不强制）。
- 帖子列表/卡片接口**不需要**该字段（卡片不渲染正文，避免放大响应体）。
- 创建接口响应若也带 mentions 更佳（前端乐观渲染直接复用），非必须。

### F3 通知语义

- 通知仅在创建时按**最终持久化名单**发一次；编辑/删除内容的后续行为由后端现有策略决定。
- 前端保证：删除 @token 后该 id 不会出现在 `mention_user_ids`，天然不产生多余通知。

## 4. 匹配契约（前后端共同遵守）

- 前端用 `mentions[].username` **原文**与正文 token 做**大小写不敏感**精确比对。
- 因此要求：**username 全局唯一（大小写不敏感意义下）**。若存在大小写不同重名
  （`john` / `John`），以 mentions 数组逐条绑定为准（数组即权威映射），前端不做全局反查。
- username 可含空格（如 `John Doe`），前端正则已支持整名匹配。

## 5. 兼容与降级

- `mentions` 缺失/空数组 → 前端回退现有文本反查（搜索回查）路径，**不报错**。
- 旧内容后端可不做数据回填；可在详情接口做**惰性补建**（首次读取时按 mention 关系生成）
  ，非必须。
- 本需求不改任何请求入参，无破坏性变更。

## 6. 验收标准

1. 发帖/评论带 @提及（含带空格用户名）→ 后端落库，通知名单 = 最终落库名单。
2. 帖子/评论详情接口回传 `mentions`（含 id+username），与落库名单一致。
3. 前端渲染零 `/user/search` 轮询：新建内容提及在冷缓存下首刷即整名建链、点击跳转正确。
4. 删 @token 后提交 → 该用户不落库、不通知。
5. `mentions` 缺失时渲染正常（回退路径），控制台无错误。
